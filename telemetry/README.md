# Telemetry server

Cartouche sends what its players' games measured to a server of the project's own: a Cloudflare Worker, [`worker.js`](worker.js), and its D1 database, [`schema.sql`](schema.sql), created in the EU jurisdiction, where it is stored and run. Telemetry is on unless the player turns off **Game measurements** on the System page ([decision 35](../docs/decisions.md)); what it sends, and what it never sends, is in [docs/privacy.md](../docs/privacy.md). The app's side is [`CartoucheTelemetry.swift`](../launcher/Sources/CartoucheTelemetry.swift), the report format [`CartoucheTelemetryReport.swift`](../launcher/Sources/CartoucheTelemetryReport.swift) and the reading of a game's log [`CartoucheGameLog.swift`](../launcher/Sources/CartoucheGameLog.swift). Cartouche Builder, on the Mac, sends its own events to the same server, unless the player turns off **Send usage measures** in its settings ([Cartouche Builder](#cartouche-builder), [`BuilderTelemetry.swift`](../builder/mac/Sources/BuilderKit/BuilderTelemetry.swift)).

The Worker has no dependency and no build: the file is deployed as it is. The project reads what it holds on a [dashboard](#dashboard) of its own, and its sessions in the cloud, which cannot reach Cloudflare, in an [export](#export) encrypted for each of them.

## Routes

- `POST /v1/reports` takes `{"reports": [...]}`, up to 25 reports in 64 KiB, and answers `{"accepted": n, "refused": m}`. Cartouche then drops them from its queue, the refused ones too, which would never be taken.
  - 400 or 413: not a batch of reports. Cartouche drops it as well.
  - 429 with `Retry-After: 60`: the address sent more than 120 requests in the minute. The count is kept in the Worker's memory only, never written.
  - 503 with `Retry-After: 3600`: the database is unavailable, or past its daily limit. Cartouche keeps its reports and tries again later.
- `POST /v1/forget` takes `{"install": "<number>"}` and deletes every report of that copy of Cartouche, and its count of the day: **Erase what this iPhone sent** on Cartouche's Game measurements page. Cartouche then takes a new number.
- `POST /v1/problems` takes a problem a player sends from **System › Report a problem** with **Send to Cartouche** ([`CartoucheProblemReport.swift`](../launcher/Sources/CartoucheProblemReport.swift)), and files it as an issue of the project's private repository, in the bug report form's sections ([Problems](#problems)). It answers 201 when GitHub has it, 200 when it had it already, and 202 when the server keeps it for its daily run: Cartouche says it is sent in all three.
  - 400 or 413: not a problem the server takes.
  - 429 with `Retry-After: 3600`: the address sent more than 10 problems in the hour, or the server took 50 today.
  - 503 with `Retry-After: 3600`: the database is unavailable.
- `POST /v1/games` takes `{"name": "Unravel TWO", "platform": "switch"}`, the name of a game of the player's that Cartouche's catalog does not know, as its copy gives it or as the player renamed it, and its platform, `switch` or `switch2`, when Cartouche can tell it from the game's title ID or the player chose it ([`CartoucheGameLookup.swift`](../launcher/Sources/CartoucheGameLookup.swift)). It looks the game up on IGDB as [`igdb_covers.py`](../catalog/tools/igdb_covers.py) looks up the catalog's games, and answers `{"found": true, "igdb": 103281, "name": "Unravel Two", "cover": "…", "artwork": "…", "genre": "puzzle", "summary": "…", "platform": "switch"}`: IGDB's game ID and name, the image IDs of its cover and of an artwork, its genre as one of Cartouche's, its summary on IGDB, in English, without web addresses, with its spaces made plain and at most 2,000 characters, and its platform; or `{"found": false}` when IGDB has no game close enough. The server asks IGDB with the Twitch application of its secrets `IGDB_CLIENT_ID` and `IGDB_CLIENT_SECRET`, which the deploy gives it, and keeps its answer for that name 30 days, so that IGDB is asked once a month at most for a game, whoever has it.
  - 400 or 413: not a name the server takes: up to 128 characters, and `switch` or `switch2` if a platform.
  - 429 with `Retry-After: 3600`: the address asked for more than 60 names in the hour.
  - 503 with `Retry-After: 3600`: IGDB cannot be asked, or the server asked it for 1,000 names today, or the database is unavailable. An answer the server kept before still comes.
- `GET /` answers `Cartouche telemetry`, to check that it runs.

## What the server keeps

Each report is checked field by field and kept as the server rebuilt it: a field it does not know, or whose value is not of the form it expects, is left out, and a report without what every report has is refused: `schema`, `kind`, `id`, `seq`, `install`, `cartouche`, `device` and `ios`, with `session`, `minutes` and `reader` for a session and `name` for an event. A report over 8 KiB is refused. So nothing the app did not mean to send can be kept, such as a path or a line of a log.

- `reports`: one row per report, its `id` once whatever the times it is sent. The report itself is `body`, and the columns beside it are what queries read: `kind`, `install`, `day`, `seq`, `cartouche`, `device`, `ios`, `game`, `name` and `session`. `day` is the day the server received it, in UTC: there is no time, and no address.
- `daily`: how many reports each copy of Cartouche sent each day, for its cap of 2,000 a day; the counts of the days before yesterday go.

- `problems`: each problem a player sent, as its issue's title and body, until GitHub has it; then only its `day` and its `issue`'s number, for the daily cap, until the day after.

- `lookups`: what IGDB has of each game looked up for `POST /v1/games`, by its `name` made plain after the platform the app said, such as `switch:unravel two`: the `answer`, as the route gives it, or nothing when IGDB has none, and the `day` IGDB was asked. Never who asked, nor from where.

Every day at 03:17 UTC, the reports older than 25 months go, the games looked up more than 30 days ago go, and the problems GitHub does not have yet are filed, 25 at most.

## Problems

A problem is the report of **System › Report a problem**, as Cartouche makes it of an error, with what the player wrote: `schema` (1), a random `id` in lowercase, so that a problem sent again after an answer that did not reach the app is filed once; `title`, the first line the player wrote; `what`, all of it; `device`, `ios` and `version`, as the bug report form's fields have them, such as `iPhone19,4 (A20 Pro, 12 GB)`, `27.3 (25B72)` and `0.10.0 (1a2b3c4)`; and `logs`, the report itself, with this iPhone's entry for `catalog/devices.json` and the reports of the last errors. Cartouche has taken the player's names and addresses out of all of it; the server takes out control characters, and refuses a problem whose fields are not of that form, or longer than it takes: 256 characters for the title, 16,000 for `what`, 60,000 for the logs.

The issue is written as GitHub writes one of the [bug report form](../.github/ISSUE_TEMPLATE/bug_report.yml)'s, so that [`catalog/tools/add_device.py`](../catalog/tools/add_device.py) reads the iPhone's measurement out of it as out of a public one. The repository is private: problems sent from Cartouche are not public, unlike those posted through GitHub's form.

## Reports

Every report carries `schema` (1), `kind`, a random `id` of its own, `seq`, the number of the report from this copy of Cartouche, and its context: `install`, the random number of this copy of Cartouche, new every 13 months and when the player erases what it sent; `cartouche`, its version; `device`, the model identifier, such as `iPhone19,4`; `ios`; `language`, the one Cartouche shows; `memoryLimitMiB`, the limit iOS sets for Cartouche and its games; and `increasedMemoryLimit`.

**A session** (`"kind": "session"`), one for each game session, read from the log nxnative writes for it after the game ended:

| Field | What it is |
| --- | --- |
| `session` | A random number of the session. A log read again because it grew comes back as a new report with the same `session`: the one with the highest `seq` counts. |
| `game`, `gameVersion` | The title ID, and the game's version as its build says. |
| `nxnative`, `nxnativeChanged` | The nxnative commit the game was built from, its first 12 digits, and whether the build had changes of its own. |
| `settings` | The game's nxnative settings, `DM_` keys only, with values of up to 32 letters, digits and `._:+-`. |
| `minutes` | How long the session lasted: from when its log was created to its last line. |
| `reader` | Which reading of nxnative's log made the measures (`CartoucheGameLogReader.version`). |
| `frames`, `targetFps` | The last frame counted, and the frame rate the game asked for. |
| `fps` | `median` and `low5`, the frame rate of the slowest 5% of the time, weighted by time. |
| `frameMs`, `gpuMs` | Milliseconds per frame and of GPU work: `p50`, `p95`, `p99`. |
| `overTargetPercent`, `droppedPercent` | Frames longer than one frame at the target rate; frames shown late or not shown. |
| `stutters` | Frames clearly longer than those before them: `count`, `perMinute`, and what they waited for: `shaders`, `textures`, `other`. |
| `shaderStallMsPerMinute` | What the game waited for new pipelines and shader libraries. |
| `prepare` | The pipeline preparation before the first frame: `seconds`, `lines`. |

| `upscaler` | `metalfx` or `bilinear`, and its `gpuMs`. |
| `audioUnderrunsPerMinute`, `display`, `dlc` | Audio underruns; `tv` and `foldSplit`, the iPhone Duo's fold between picture and controls; whether the game loaded downloadable content. |
| `end` | How the session ended: `kind` (`crash`, `boot-failed`, `memory-likely`, `quit`, `unknown`), and for a crash its `signal` and where, as module and offset: `pc`, `lr`. Only a game that ran behind the console says the player quit it. |
| `process` | What the game's own process wrote of its memory every two seconds, when it ran behind the console ([`CartoucheGuest.m`](../launcher/LiveProcessSupport/CartoucheGuest.m)): `limitMiB`, the limit iOS set for that process; `peakMiB`, its peak as iOS counts it, which `memory.peakMiB` takes too; `lastAvailableMiB`, what iOS still let it use at its last reading; `quit`, whether the player quit it rather than iOS ending it; and `screens`, the last 10 sizes its screen took, in points, each with the `minute` it took it and the `footprintMiB` then. |

A value the log does not have is left out.

| `app.updated` | The first start of a new version. | `from`, `to` |

| `game.installed` | A game installed or updated. | `version`, `nxnative`, from the game's Info.plist: up to 0.11.2, Cartouche read them, as a session's `gameVersion` and `nxnative`, from LiveContainer's settings for the game, which hold neither, and sent none |

| `signing.imported` | A signing certificate went in, or did not, in a Cartouche installed with the player's own certificate. | `via`: `installer`, the one the Cartouche Installer handed over for the first start, or `setup`, one the player chose in **Import signing certificate**; `outcome`: `imported`, or why not: `handoff` (the installer's file did not open), `invalidKey`, `invalidProfile`, `reinstall` (the profile Cartouche was installed with does not allow it), `refused` (iOS refused what it signs), `busy`, `keychain`, `other`. | `import.picker` | The Files picker of an import closed; one still open when Cartouche ended is told at the next start. | `outcome`: `picked`, `cancelled`, `closed` with the controller's B, `lost` when it left the screen or never came without an answer, `quit` when Cartouche ended with it open; `place`, where the player opened it (`home`, `sheet`, `guide`); `seconds`, how long it was open; `shownMs`, how long it took to come on screen; `longestStallMs` and `stalls`, the longest Cartouche's main thread, which passes the picker every touch, took to answer meanwhile, and how many times it took over half a second; `background`, whether Cartouche went to the background meanwhile; `controller`, whether a game controller was connected |

An error's `cause` is one name of [`CartoucheFailure.Cause`](../launcher/Sources/CartoucheFailure.swift) (`appleCredentials`, `anisette`, `vpn`, `pairing`, `device`, `noSpace`, `storageOffline`, `network`, `other`...), which Cartouche tells from the error's codes, its kind and the step reached, the deepest error that tells one winning. `stage` is the step it stopped at, a name (`unpacking`, `signing`, `connect`, `savesSync`...); `percent` how far it got; `seconds` how long it ran. An error of the storage also says its `kind` (`signInFailed`, `folderGone`...) and, for the server's own status, `protocol`, `status` and `statusCode`; an install, the error LiveContainer gave (`latestCertificateInvalid`...).

The Apple ID sign-in, the registration of this iPhone alone, Refresh All Apps and Update Cartouche run in the built-in SideStore, whose error comes back to Cartouche as text alone. SideStore now also leaves Cartouche how they ended, in a keychain item they share ([patch 0014](../app/patches/sidestore/0014-tell-cartouche-where-its-actions-stopped-and-why.patch)), and Cartouche sends of it: `stage`, the sign-in's own step (`credentials`, `deviceCheck`, `account`, `verification`, `team`, `certificate`, `device`, `finish`), that of the iPhone's registration alone (`account`, `deviceCheck`, `device`, `finish`), or the last operation started (`ResignApp`); `trail`, the operations before it; `kind`, the case of SideStore's error (`noDevice`, `incorrectCredentials`, `underlyingError`...); `apple`, Apple's code; `http`, a server's HTTP status; for an HTTP error of Apple's without an answer of its own, such as its 429, Too Many Requests ([patch 0016](../app/patches/sidestore/0016-tell-apples-too-many-requests-apart-from-its-answers.patch)), `service`, which of Apple's services gave it (`grandSlam`, the sign-in and its verification code; `developerServices`; `other`), and `retryAfter`, the seconds Apple asked to wait, when it did; `network`, a network error's code, with `host`, what the server was (`apple`, `anisette` for the anisette servers a sign-in uses since [patch 0015](../app/patches/sidestore/0015-sign-in-as-the-cartouche-installer-does.patch), `sideStore`, `github`, `device`, `other`); `codeAsked` and `codeMode`, whether and how Apple asked for a code; `certificates`, `bundledCertificate`, `activeCertificate`, `teams`, `teamType`. With them, `vpn` and `pairing`: whether the VPN was on and the pairing file in place. A sign-in that went through and left LiveContainer without a certificate it can open is an error of Cartouche's own, at the stage `handOff`, with the cause `certificate`. When SideStore left nothing, the cause comes from the sentences LiveContainer's bridge fails with (`sideStoreQuit`, `sideStoreSlowStart`...), or is `noOutcome`. When Apple refuses more requests for now, its HTTP 429 or its codes for too many attempts (-20102, -21668, -22411), the cause is `tooManyAttempts`, and a sign-in also sends `wait`, the seconds Cartouche then keeps the player, and itself, from signing in again, and `inARow`, how many sign-ins in a row Apple refused so. A page of Apple's in SideStore's words, as before patch 0016, gives its status alone, as `http`. From the version of November 13 ([patch 0018](../app/patches/sidestore/0018-tell-cartouche-the-error-behind-sidestores-titles.patch)), an error SideStore wrapped in a title, as its refresh and its updates do, gives the `kind`, Apple's code and the HTTP status of the error it wraps, where it gave `ALTWrappedError` and no code; and, for its `invalidParameters`, which it throws for what its own code did not expect, `reason`, which of its sentences it was (`notInContext`, `askTeam`, `noStepWeight`...), and `missing`, the step or the value that sentence names (`targetAppBundle`), never the sentence. Since [patch 0019](../app/patches/sidestore/0019-check-the-iphone-before-signing-in-and-register-it-alone.patch), a sign-in checks that it reaches this iPhone, through LocalDevVPN, before it sends anything to Apple: one that stops at `deviceCheck` cost the player no verification code. One that stops at `device` all the same leaves only this iPhone to register, which Cartouche does alone, without a sign-in: its error also sends `deviceOnly`; with `automatic` when Cartouche started it by itself. A sign-in's error, and that of the iPhone's registration, send `vpnWait` and `withoutVPN` as `account.signedIn` does. Every value is checked again in Cartouche: a name a programmer gave, a number in its range, never words.

## Cartouche Builder

It never sends a path, a file or folder name, a game's name, a log line, an error's words, the Mac's name or the names of the paired iPhones. [`test/builder-reports.json`](test/builder-reports.json) holds one report of each, which the server's tests check it keeps whole, and which the app's tests check it makes ([`TelemetryTests.swift`](../builder/mac/Tests/BuilderKitTests/TelemetryTests.swift)).

## Dashboard

[`dashboard/`](dashboard/) is a second Worker, `cartouche-dashboard`, which reads the same database and shows what it holds on one page, for the project alone: [`dashboard/worker.js`](dashboard/worker.js) and its page, [`dashboard/index.html`](dashboard/index.html), deployed with the server, the page with the catalog's names and covers of the games and the chips of the iPhones ([decision 43](../docs/decisions.md)).

It opens only behind **Cloudflare Access**: without it, every request gets a page that says the dashboard is closed, and nothing of the database. Who may sign in, with their Cloudflare account or with GitHub, is the Access policy's to say. Once, by hand:

1. Zero Trust, on its Free plan, for the account: [one.dash.cloudflare.com](https://one.dash.cloudflare.com/), with a team name. It asks for a payment method, even for the Free plan.
2. **Workers & Pages › cartouche-dashboard › Access › Protect this Worker behind Access**, for **All traffic**, with the policy **Cloudflare account**: the account's members sign in with their Cloudflare account. This Worker only: the server, `cartouche-telemetry`, stays open to the iPhones, which have no account to sign in with, and the deploy fails when Access protects it.
3. To sign in with GitHub as well: a GitHub OAuth app ([github.com/settings/applications/new](https://github.com/settings/applications/new)) whose homepage is `https://<team>.cloudflareaccess.com` and callback `https://<team>.cloudflareaccess.com/cdn-cgi/access/callback`; its client ID and a client secret in **Zero Trust › Integrations › Identity providers › Add new › GitHub**; and in the dashboard's policy, an **Emails** rule with the GitHub account's address.

The runtime hands the Worker who Access signed in (`ctx.access`). Behind a hostname's Access application instead, the deploy's variables `CLOUDFLARE_ACCESS_TEAM`, the team's name, and `CLOUDFLARE_ACCESS_AUD`, the application's audience tag, let the Worker check the token Access adds to each request against the team's keys. The deploy's summary says whether Access protects the dashboard.

- `GET /` is the page; `GET /data?days=N` the reports of the last N days, 28 unless asked, 400 at most, as compact rows, which the page sums up itself. D1 writes them as JSON, 2,000 at a time, newest first, and the Worker passes them on without reading them, within the free plan's 10 ms of CPU and its 50 queries a request: past them, the oldest reports of the window are left out, and the page says so. A copy's random number, and a session's, leave cut to their first 8 digits. With them go what the server took today and yesterday, the problems GitHub does not have yet, and the issues of the problems' repository, without their bodies.
- The page shows the period at a glance, then each game, with its cover loaded from IGDB by its ID as the app does; the days; the frame rate, frame and GPU times, stutters and settings; heat and power; memory against iOS's limit; how sessions ended, and crashes by signal and address; devices, versions and storage; installs; errors by origin, cause and code, and the Apple ID sign-in's successes, failures and the step they stopped at; every event by name, those it does not detail yet as well; the problems players sent; Cartouche Builder's Macs; and the server's use of its free plan. A game, a model or a version picked filters the whole page; `?demo` shows it with made-up data.
- It sets no cookie of its own and loads nothing but its data and IGDB's images, without the page's address; its scripts run under a nonce of each answer, and no other site may frame it.

## Game sheets

Each Thursday, the Game measurements workflow ([`.github/workflows/measurements.yml`](../.github/workflows/measurements.yml)) sums up the sessions of the 28 days before into the results of the game sheets in [`catalog/games/`](../catalog/README.md), with [`sheets.py`](sheets.py), in time for Friday's version:

- For each sheet, and each iPhone model at least three iPhones played the game on, one result. A copy of another region counts for its game, and a session sent again counts once, at its highest `seq`. A model fewer iPhones played the game on gets no result, and a figure fewer than three iPhones measured is left out: the sheets show figures of several iPhones, never of one.
- Its figures are medians of each iPhone's own median, so that each iPhone counts once, however much it played: the frame rate, that of the slowest 5% of the time, the stutters a minute and the memory peak, each iPhone's highest. With them, how many sessions ended badly: crashed, never drew a frame, or ran out of memory. They are in its `measured`, and said in its note.
- Its status: `does-not-run` when no session drew a frame; `boots` when half of the sessions or more ended badly; `playable-with-issues` when a tenth of them or more did, or the frame rate is under 90% of the rate the game asks for, or that of the slowest 5% of the time under 75% of it; `playable` otherwise.
- Its engine is the nxnative build most sessions ran, and how many others did; its iOS the version most of the iPhones run.

The results testers wrote stay as they are. A measured result is replaced by its model's new one, and stays while its model has none. The sheets that changed go on the branch `catalog-measurements`, whose pull request goes through CI before it is merged; the job summary links it, with how many sessions and iPhones were summed up. The workflow reads the database with the same secrets as the deploy, and does nothing without them.

## Export

The project's sessions in the cloud run where the network does not reach Cloudflare, and the dashboard opens only behind Access: they read the database through the **Telemetry export** workflow ([`.github/workflows/telemetry-export.yml`](../.github/workflows/telemetry-export.yml)) and [`export.py`](export.py), which only those who can write to the repository can run.

1. `python3 telemetry/export.py key --out DIR` makes a key pair: the private key in `DIR/export-key.pem`, readable by its owner only, which never leaves the session; it prints the public key.
2. The workflow, run on `main` with that key, and `days` to keep only the last days, reads the database with the deploy's secrets into a SQLite file, and encrypts it for the key. Its second job, which holds no secret, puts the export on the branch `telemetry-export`, in place of the one before.
3. `git fetch origin telemetry-export`, then `python3 telemetry/export.py open --key DIR/export-key.pem --ref FETCH_HEAD --out FILE`, checks that the export was made for this key and decrypts it into `FILE`, outside the repository.

What leaves the database is what the dashboard reads, and no more. In `reports`, each report as the server kept it, without its own `id`, with `install` and `session` cut to their first 8 digits: `n` is the order the server received them in, and `body` the report, which SQLite's JSON functions read, such as `json_extract(body, '$.fps.median')`. In `daily`, how many reports each day brought and from how many copies; in `problems`, the day of each problem and whether GitHub has it, never its words, which the problems' private repository holds; in `export`, what the export holds.

The SQLite file is gzipped, then encrypted with AES-256-CBC under a random key; that key, with the SHA-256 of what it encrypts, goes in an envelope encrypted with RSA-OAEP (SHA-256) for the public key, an RSA key of 3072 bits or more. The branch, as public as the repository, shows nothing but the manifest, `export.json`: the key's fingerprint, the run and when; and the job's log nothing of what the database holds.

## Deploy

[`.github/workflows/telemetry.yml`](../.github/workflows/telemetry.yml) tests the server on each pull request that changes it, and deploys it from `main` with [`deploy.sh`](deploy.sh), which calls Cloudflare's API with curl and jq: the database, created in the EU jurisdiction if it is not there yet; `schema.sql`, whose every statement runs again without harm; the Worker, with the database bound as `DB` and no logs kept; its `workers.dev` address; and its daily run. The job summary gives the address, which goes in [`app/config.env`](../app/config.env) as `CARTOUCHE_TELEMETRY_URL`: a build with none sends nothing. The deploy then asks both addresses what they answer: the server its name, and the dashboard Access's sign-in or its closed page. A server that sends to Access's sign-in instead could take nothing from the iPhones: the run fails, and says where to take it out of Access.

The deploy takes two secrets of the repository's environment `cloudflare`, and does nothing while they are not set:

- `CLOUDFLARE_API_TOKEN`: a token of the account with **Account › Workers Scripts › Edit** and **Account › D1 › Edit**;
- `CLOUDFLARE_ACCOUNT_ID`: the account's ID.

A third, `CARTOUCHE_REPORTS_TOKEN`, lets the Worker file problems: a fine-grained token of the repository `<owner>/cartouche-reports` alone (or the variable `CARTOUCHE_REPORTS_REPOSITORY`), private, with **Issues › Read and write**. The deploy binds it to the Worker as the secret `PROBLEMS_TOKEN`, with the repository as `PROBLEMS_REPOSITORY`, once it has checked with GitHub that the repository is private: it binds nothing to a public one. Without it, the server keeps the problems players send, and files them at the first daily run after a deploy with it. The job summary says where problems go.

Run the workflow by hand for a first deploy once they are set. The free plan is enough: 100,000 requests and 100,000 rows written a day.

The deploy also uploads the [dashboard](#dashboard), with the same database and problems' repository, on its own `workers.dev` address, and does it again when the catalog's names, covers or devices change on `main`.
